PROJECT 01 · eXemble

QA 없는 팀의 AI Agent 기반 E2E 테스트 체계

팀원 모두가 Playwright를 배우는 대신 AI가 테스트를 작성하게 하고, AI가 틀리지 않도록 규칙과 구조를 먼저 설계한 작업입니다.

제품
LLM 애플리케이션·에이전트 워크플로우 플랫폼
역할
테스트 체계 설계 · Helper와 규칙 · AI Agent 구축
기술
Playwright · Claude Code · GitHub Actions
링크
기술 블로그 ↗ · 상세 글 ↗
문제
QA 인력 없이, 배포 전마다 개발자가 사용자 흐름을 손으로 확인했습니다. 기능이 적을 때는 약 20분이면 됐지만, 제품이 커지면서 전체를 손으로 확인할 수 없게 됐습니다.
한 일
디자인 시스템과 1:1로 대응하는 Helper 6종과 실패 4분류 규칙을 먼저 만들고, 그 위에서 AI Agent가 테스트를 작성·실행·수정하게 했습니다.
결과
  • 배포 전 전체 검증을 CI E2E 자동 실행으로 대체
  • 최근 3번 배포에서 회귀 6건 사전 탐지
  • SPEC 커버리지 8% → 49%

01해결하려던 문제

팀에 QA 인력이 없어서, 배포 전마다 개발자가 "이 버튼을 누르면 이 모달이 뜨고, 확인을 누르면 이 화면으로 가는지"를 손으로 확인했습니다. 기능이 적을 때는 한 번에 약 20분이면 됐지만, 기능이 늘수록 확인할 분기도 같이 늘어 지금 규모에서는 전체를 손으로 확인할 수 없습니다.

테스트를 자동화하려 해도 팀원 모두가 Playwright를 깊이 익힐 시간이 없었습니다. 그렇다고 AI에게 "알아서 써 달라"고 하면 매번 다른 스타일로 불안정한 코드가 나왔고, UI가 조금만 바뀌어도 테스트가 한꺼번에 깨졌습니다.

02구조: AI가 테스트를 쓰고, 고치고, 멈추는 지점

03판단과 이유

유닛 테스트가 아니라 E2E로 시작한다
상황
사람이 하던 수동 검증은 이미 "버튼 → 모달 → 화면 이동" 같은 사용자 플로우 단위였습니다.
판단
유닛 테스트로는 이 흐름 전체를 검증하기 어렵습니다. 지금 사람이 하는 검증을 그대로 옮기는 것이 가장 직접적인 자동화라고 보고 E2E를 택했습니다. 병렬 실행, 접근성 기반 selector, trace 수집이 기본 제공되는 Playwright를 골랐습니다.
AI에게 맡기기 전에, AI가 따를 API를 만든다
상황
규칙 없이 Playwright API를 그대로 쓰게 하면 AI는 매번 다른 방식으로 요소를 찾고, 같은 패턴을 열 군데에 풀어 썼습니다.
판단
디자인 시스템 컴포넌트와 1:1로 대응하는 Helper 6종(Dialog, Form, Select, Table, Navigation, Toast)을 만들어 fixture로 주입했습니다. AI는 form.fillFields(), dialog.clickConfirm()처럼 자연어에 가까운 메서드만 알면 되고, UI가 바뀌면 Helper 안쪽만 고치면 됩니다.
AI가 모든 실패를 고치게 두지 않는다
상황
스스로 고치는 에이전트는 실제 앱 버그까지 테스트 수정으로 덮어 버릴 수 있습니다. 그러면 테스트는 초록불인데 버그는 그대로 배포됩니다.
판단
실패를 4가지로 나눠, UI 변경과 테스트 버그만 고치게 했습니다. 앱 버그와 환경 문제는 코드를 건드리지 않고 보고하며, 앱 버그는 단언을 그대로 둔 채 보류 표시와 버그 목록으로 남깁니다. 대기·재시도를 넣어 버그를 피해 가는 것은 금지했습니다.
AI가 실행 결과를 직접 보게 한다
상황
같은 테스트를 Claude에게 직접 요청했을 때는 5~6번 수정을 주고받아도 계속 실패했습니다. 실행 결과를 보지 못하니 원인을 짚지 못했습니다.
판단
에이전트가 직접 실행하고, 에러 로그와 trace 스크린샷으로 원인을 분류한 뒤 고치는 루프(최대 3회)를 만들었습니다. 같은 작업이 1번에 통과했습니다.

04성과

지표 개선 전 개선 후
배포 전 전체 기능 검증 수동 약 20분
(기능이 적던 초기)		 CI에서 E2E 자동 실행

운영 배포 전 사전 탐지한 회귀 — 최근 3번 배포에서 6건

Helper 메서드만 보면 테스트를 쓸 수 있게 되면서, Playwright를 처음 쓰는 팀원도 같은 규칙으로 테스트를 작성할 수 있게 됐습니다. 매일 밤 전체 테스트를 실행해 실패하면 해당 화면을 마지막으로 고친 사람에게 태스크가 배정되므로, 테스트 유지보수도 기능을 바꾼 사람이 함께 맡게 됐습니다.

05아쉬운 점과 다음 단계

  • 처음에는 핵심 플로우 위주라 범위가 좁았습니다. 기획 문서(SPEC)의 항목과 테스트를 연결해 보니 1,739개 항목 중 8%만 테스트로 덮여 있었습니다. SPEC 항목과 테스트를 태그로 연결하고 우선순위가 높은 항목부터 작성해 49%까지 올렸지만, 아직 절반가량은 테스트가 없습니다.
  • 운영 배포 PR에서 E2E 통과를 필수 머지 조건으로 거는 작업을 진행 중입니다.

PROJECT 02 · ExTuner

직접입력 화면의 초기 로딩과 입력 지연 개선

화면 하나에서만 쓰는 대형 라이브러리가 모든 화면의 첫 진입에 실리던 구조를 끊고, 긴 SQL을 편집할 때 생기던 입력 지연을 없앤 작업입니다.

기간
2026년 3분기
역할
원인 분석 · 구현 · 측정 기준 설계
기술
React · Vite · Monaco · Orval · Lighthouse
문제
온프레미스용으로 SQL 에디터를 번들에 넣은 뒤 공통 엔트리가 약 8.3MB로 커졌고, 5만 자 SQL은 키 입력마다 0.5초 넘게 밀렸습니다.
한 일
화면 전용 라이브러리가 공통 엔트리에 포함되는 세 경로(전역 import·배럴·정적 import)를 끊고, SQL 포매터는 보이는 화면에서만 실행되게 했습니다.
결과
  • 공통 엔트리 gzip 2,442 → 363KiB
  • FCP 7.6초 → 1.3초
  • 키 입력 지연 565ms → 24ms

01해결하려던 문제

ExTuner는 LLM으로 SQL 성능을 진단하고 튜닝을 실행하는 플랫폼입니다. 고객사 온프레미스 환경에 맞춰 SQL 에디터(Monaco)를 로컬 번들에 포함했는데, 그 뒤로 공통 엔트리가 약 8.3MB까지 커졌습니다. 에디터가 없는 화면도 첫 진입 때 Monaco·ECharts·ExcelJS를 함께 내려받고 있었습니다.

SQL 직접입력 화면에서는 5만 자 SQL을 편집할 때 키 입력 하나에 0.5초 이상 지연이 생겼습니다.

그리고 하나가 더 있었습니다. 2분기 회고에서 "개선 효과를 수치로 남기지 못했다"를 부족했던 점으로 꼽았기 때문에, 이번에는 고치는 것만큼 같은 절차로 전후를 비교할 수 있게 만드는 것도 과제로 삼았습니다.

02구조: 무엇이 공통 엔트리로 새고 있었나

빌드 결과와 소스맵 시각화로 공통 엔트리에 들어온 모듈의 import 경로를 역추적해 정리한 구조입니다.

03판단과 이유

Monaco 하나가 아니라 "새는 구조"를 고친다
상황
눈에 띄는 건 Monaco였지만, 번들을 열어 보니 ECharts·ExcelJS·faker도 같은 방식으로 들어와 있었습니다.
판단
Monaco만 빼면 다음 대형 라이브러리가 같은 길로 다시 들어옵니다. 원인을 "화면 전용 의존성이 공통 경로로 새는 구조"로 정의하고, 전역 import·배럴 파일·정적 import라는 세 가지 경로를 모두 끊었습니다.
지연 로딩의 경계는 "라우트"가 아니라 "실제로 쓰는 순간"에 둔다
상황
ExcelJS는 엑셀 내보내기 버튼을 눌러야만 쓰이고, Monaco는 코드 에디터가 있는 경로에서만 쓰입니다.
판단
라우트 단위로 나누면 그 화면에 들어온 사용자는 쓰지도 않을 ExcelJS 비용을 냅니다. Monaco 설정은 에디터 사용 경로로 옮기고, ExcelJS는 버튼 클릭 시점의 동적 import로 바꿔 기능을 쓰는 사람만 비용을 내도록 했습니다.
mock을 지우지 않고 분리한다
상황
Orval이 실제 API 클라이언트와 MSW mock을 같은 파일에 생성해서, mock이 쓰는 faker가 프로덕션 번들에 함께 들어가고 있었습니다.
판단
mock 생성을 끄면 번들은 줄지만, 백엔드보다 먼저 화면을 개발하던 mock 환경이 사라집니다. Orval의 tags-split 모드로 mock만 별도 청크로 떼어 내 개발 환경은 그대로 두고 프로덕션에서만 제외했습니다. 대가로 import 경로 104곳을 고쳐야 했습니다.
고치기 전에 측정 기준부터 정한다
상황
2분기에는 개선을 해 놓고도 효과를 수치로 남기지 못했습니다.
판단
측정 화면(/manual-sql), Lighthouse 버전, 측정 조건을 고정하고, gzip 같은 서버 설정은 다른 코드 변경과 섞지 않고 따로 측정하도록 순서를 정했습니다. 키 입력 지연은 측정 스크립트로 만들어 저장소에 남겼습니다.

04마주친 문제와 해결

공통 엔트리는 크게 줄었는데, Lighthouse 점수는 1점만 올랐다

Monaco·ECharts·ExcelJS를 분리한 1차 측정에서 공통 엔트리(raw)는 8.3MB → 1.9MB로 줄었고 FCP도 7.6초 → 4.2초로 빨라졌지만, Lighthouse Performance 점수는 55 → 56이었습니다.

점수를 근거로 "효과가 없다"고 결론 내리기 전에 전송 자산을 다시 뜯어봤습니다. 측정 서버에는 아직 gzip이 반영되지 않아 모든 JS가 원본 크기로 전송되고 있었고, 프로덕션 번들에는 mock 코드가 남아 있었습니다. 점수가 안 오른 건 분리가 효과가 없어서가 아니라, 다음 병목이 바로 뒤에 서 있었기 때문이었습니다.

서버 gzip 적용과 mock 분리를 마친 뒤 배포 서버에서 다시 측정한 결과, Performance는 55 → 73, FCP는 7.6초 → 1.3초가 됐습니다. gzip이 실제로 걸렸는지는 Lighthouse 결과의 전송 크기 / 원본 크기 비율로 확인했습니다(JS 0.30, CSS 0.16).

측정하면서 틀렸던 세 가지

이 작업에서 가장 많이 배운 건 잘못 잰 경험이었습니다. 1차 기록에 적어 둔 추정 세 개가 실측에서 뒤집혔습니다.

  • 격리해서 재면 부풀려진다. faker의 크기를 보려고 별도 청크로 떼어 재니 gzip 890KB였지만, 실제로 제거하고 줄어든 건 224KiB였습니다. gzip은 큰 파일 안에 섞여 있을 때 더 잘 압축되기 때문입니다. 그 뒤로 강제 분리는 "어디 있나"를 볼 때만 쓰고, "얼마나 기여하나"는 제거 전후 비교로만 판단합니다.
  • 청크 이름은 정체를 말해주지 않는다. 4MB 크기의 TuningFilter 청크를 faker 탓으로 짚었는데, 라이브러리 고유 문자열로 검색해 보니 Monaco 문자열이 560건 들어 있었습니다. 번들러가 청크 안의 아무 모듈 이름이나 붙인 것이었습니다.
  • 기준선은 직전 커밋을 같은 머신에서 다시 빌드한다. 몇 커밋 전에 기록한 601KiB를 기준으로 썼다가, 직전 커밋을 다시 빌드하니 587KiB였습니다. 그 사이 다른 PR의 변동이 섞여 있었습니다.
긴 SQL에서 키 입력이 0.5초씩 밀렸다

입력 지연을 측정해 보니 원인은 키를 누를 때마다 실행되던 SQL 포매터였습니다. 포매팅된 SQL은 별도 보기에서만 필요했기 때문에, 그 화면이 보일 때만 포매터가 실행되도록 바꿨습니다. 함께 커진 페이지 컴포넌트를 책임별로 나눠 입력과 무관한 영역의 리렌더링도 줄였습니다.

05성과

숫자 외에도, 같은 절차로 다시 잴 수 있는 측정 스크립트와 측정 문서를 팀에 남겨 이후 성능 작업의 기준선으로 쓸 수 있게 했습니다.

06아쉬운 점과 다음 단계

  • 전체 JS 총량은 4,914KiB → 4,910KiB로 거의 그대로입니다. 코드를 지운 게 아니라 처음에 안 받아도 되는 것을 뒤로 미룬 것이라, 해당 기능에 진입하는 순간의 비용은 여전히 남아 있습니다.
  • Monaco 문자열이 섞여 있던 4MB 청크는 원인을 다시 진단했지만, 아직 분리하지 못했습니다.
  • 폰트 서브셋은 남은 과제입니다. 폐쇄망 고객사에서는 CDN 동적 서브셋을 쓸 수 없고 글리프를 잘라내는 방식은 누락 위험이 있어, unicode-range로 나눠 받는 방향을 정해 두었습니다.

PROJECT 03 · eXemble

단위 테스트 격리 해제로 CI 테스트 시간 39% 단축

테스트 파일마다 환경을 새로 만들던 비용을 걷어 내고, 그 과정에서 깨진 테스트를 "왜 깨지는지"부터 분류해 고친 작업입니다.

기간
2026.11 (5일)
역할
원인 분석 · 구현 · 전후 측정
기술
Vitest · MSW · i18next · GitHub Actions
규모
PR 5개
문제
CI 단위 테스트 job이 가장 늦게 끝났고, 시간 대부분이 테스트가 아니라 파일마다 모듈을 다시 불러오고 jsdom을 새로 만드는 데 쓰였습니다.
한 일
격리를 기본으로 끄고, 상태가 다음 파일에 남는 18개와 vi.mock 파일만 격리 실행했습니다. 깨진 87개 파일은 원인별로 나눠 고쳤습니다.
결과
  • CI 단위 테스트 p50 140초 → 85초
  • p90 214초 → 127초
  • 로컬 CPU 사용량 −64%

01해결하려던 문제

프론트엔드와 백엔드의 PR 검사가 CI 서버 한 대에서 돌면서 서버 대기열이 최대 89까지 찼고, 프론트엔드 PR 검사에서는 단위 테스트 job(192초)이 가장 늦게 끝났습니다.

시간 대부분은 테스트 자체가 아니라, 파일마다 모듈을 다시 불러오고 가상 DOM(jsdom)을 새로 만드는 데 쓰이고 있었습니다. 격리를 끄면 CPU 사용량이 약 80% 줄었지만, 대신 87개 파일이 실패했습니다.

02구조: 격리가 필요한 파일만 격리한다

새로 추가되는 테스트 파일은 기본으로 격리 없이 돌고, 문제가 확인된 파일만 목록에 넣는 방식입니다.

03판단과 이유

번역 처리: 세 가지 방법 중 "키 그대로 출력"을 고른다
상황
격리를 끄면 파일들이 i18n 상태를 공유하는데, 테스트마다 번역을 다루는 방식이 한국어 문장 단언, 키 단언, react-i18next mock(47곳)으로 제각각이었습니다.
기각
실제 한국어 리소스로 통일하면 고칠 단언이 약 120~180건이고, 문구를 바꿀 때마다 테스트가 깨집니다. react-i18next를 전역 mock하면 i18next를 직접 쓰는 헬퍼는 덮이지 않아 방식이 두 가지로 남습니다.
판단
번역 키를 그대로 출력하는 cimode로 통일했습니다. 이미 키로 단언하던 약 72개 파일과 결과가 같았기 때문입니다. 대신 키가 리소스에 실제로 있는지는 테스트가 확인하지 못한다는 비용을 받아들였고, 번역 문장 자체가 검증 대상인 파일만 한국어로 바꿔 실행합니다.
검증 기준을 현실에 맞게 낮춘다
상황
처음 기준은 "실행 순서를 섞어 5번 모두 통과"였는데, 회차마다 처음 보는 파일이 1~3개씩 실패해 작업이 끝나지 않았습니다.
판단
"CI와 같은 순서로 3번 통과, 순서를 섞었을 때 실패한 파일은 격리 목록에 넣는다"로 바꿨습니다. 모든 누수를 미리 잡는 대신, CI에서 새로 깨지는 파일이 나오면 목록에 넣는 PR로 막는 쪽을 택했습니다.
실행 방식: Vitest를 두 번 돌린다
상황
Vitest 3은 격리 여부를 프로젝트별로 나눠 걸 수 없고, 실행 풀(threads)로 나누는 방법은 CI에서 메모리 부족으로 실패했습니다.
판단
스크립트 하나가 격리 없는 실행과 격리 실행을 차례로 돌리고, CI도 같은 스크립트를 쓰게 했습니다. 로컬과 CI가 같은 명령으로 돌기 때문에 결과가 어긋나지 않습니다.

04마주친 문제와 해결

첫 버전은 격리가 실제로 꺼지지 않았다

격리를 끄는 설정을 넣었는데 CI와 로컬 시간이 그대로였습니다. Vitest 3에서는 이 설정을 프로젝트별로 나눠 걸 수 없어서, 넣은 위치에서는 적용되지 않고 있었습니다. 이 버전으로 측정한 비교(중앙값 110초 대 114.5초)는 무효로 처리하고 다시 쟀습니다.

원인을 셋으로 나눠 따로 고쳤다

실패한 파일을 원인별로 나눴습니다. 스토어·타이머·전역 값이 다음 파일로 새는 경우는 setup에서 정리하고, 다른 파일의 vi.mock 때문에 깨지던 11개와 원인이 불분명했던 21개를 정리해 격리 목록에서 뺐습니다. Codex 코드 리뷰에서는 MSW 요청 리스너가 첫 파일 이후 사라지는 문제가 나와 함께 고쳤습니다. 같은 목록 파일을 고치는 PR 3개는 순서를 정해 하나씩 머지하고 매번 rebase했습니다.

05성과

지표 개선 전 개선 후 변화
CI 단위 테스트 단계 p50 140초 85초 −39%
CI 단위 테스트 단계 p90 214초 127초 −41%
로컬 전체 실행 시간 약 170초 약 75초 −56%
로컬 CPU 사용량 약 1,340 CPU초 약 480 CPU초 −64%
격리 실행 목록 67개 파일 18개 파일 −49개

CI 기준선은 머지 전 29회, 머지 후는 22회 실행의 "테스트 실행 단계"만 잰 값입니다(설치 단계 제외). CI 서버 부하에 따라 106~300초까지 편차가 커서 1회 측정으로 판단하지 않았습니다.

06아쉬운 점과 다음 단계

  • 머지 후 표본이 이틀치뿐입니다. 그 사이 CI 실행 기록이 지워져 있었습니다. 다음에는 머지 직후부터 바로 기록을 모아 둘 생각입니다.
  • 격리 목록 18개와 vi.mock을 쓰는 파일 62개가 아직 격리 실행에 남아 있습니다. feature flag는 MSW 응답으로, toast는 spy로 바꾸는 두 묶음만 처리해도 11개 파일을 더 뺄 수 있습니다.
  • 순서를 섞었을 때만 실패하는 테스트 하나는 같은 조건으로 재현되지 않아 원인을 찾지 못하고 목록에 넣어 두었습니다.

PROJECT 04 · eXemble

6개 화면이 따로 쓰던 트리를 공용 컴포넌트 하나로

상태를 고치는 곳이 셋이던 트리에서 상태의 주인을 정하고, 조회는 화면에 맡겨 여러 화면이 같은 트리를 그대로 쓰게 만든 작업입니다.

역할
설계안 제안 · 구현 · 기존 화면 교체
기술
React · TypeScript · react-arborist
문제
기능이 늘수록 공용 트리의 수정 영향 범위를 예측할 수 없었습니다. 새 기능이 필요한 화면은 트리를 따로 만들었고, 데이터를 갱신하면 선택이 풀렸습니다.
한 일
조회는 화면이, 데이터와 UI 상태는 트리가 맡도록 나누고, 상태 변경을 공통 함수 하나로 모았습니다. 선택은 객체 대신 ID로 관리했습니다.
결과
  • 6개 화면의 트리를 공용 컴포넌트 1개로 통합
  • 상태 변경 경로 훅 3곳 → 공통 함수 1개
  • 조회 기준 변경에 트리 수정 없이 대응

01해결하려던 문제

한 화면용으로 만든 공용 트리를 여러 화면이 쓰게 되면서, 기능이 늘어날수록 한 곳을 고쳤을 때 어디까지 영향이 가는지 예측하기 어려워졌습니다. 새로운 기능이 필요한 화면에서는 기존 컴포넌트를 확장하기 어려워 별도의 트리를 구현해야 했습니다.

데이터를 갱신하면 같은 노드도 새 객체로 만들어져, 사용자가 선택해 둔 노드의 선택이 유지되지 않는 문제도 있었습니다.

02구조: 상태를 고치는 곳을 하나로

03판단과 이유

개별 오류가 아니라 상태의 소유권을 다시 정한다
상황
확장이 어려운 문제와 선택이 풀리는 문제는 따로 보였지만, 상태 변경 경로를 추적해 보니 데이터 조회, 자식 노드 로딩, 드래그 앤 드롭을 맡은 세 훅이 같은 트리 상태를 각자 수정하고 있었습니다.
판단
오류를 하나씩 고치면 상태를 바꾸는 경로 셋은 그대로 남습니다. 개별 오류 대신 상태의 소유권과 트리의 책임 범위를 다시 정했습니다.
조회는 트리가 아니라 화면이 맡는다
상황
처음에는 트리 훅이 초기 조회, 자식 노드 로딩, 상태 갱신까지 모두 맡도록 설계했습니다. 화면마다 API가 달라서, 훅에 API를 넘겨주는 방식을 먼저 시도했습니다.
기각
TanStack Query 옵션을 넘기는 방식은 유연해 보였지만 트리가 특정 서버 상태 라이브러리에 묶였습니다. API 함수를 넘기는 방식은 실제로 구현해 보니 성공·실패 처리까지 훅이 떠안아 책임이 커졌습니다. 두 방식 모두 상태의 주인은 하나가 되지만, 트리가 화면별 API와 서버 상태 관리 방식에 종속됩니다.
판단
화면마다 다른 것은 조회 방식이고, 모든 화면에 같은 것은 트리 상태를 다루는 규칙이었습니다. 조회는 화면이 맡고, 트리는 전달받은 데이터와 UI 상태만 관리하도록 나눴습니다.
상태 변경은 공통 함수 하나로, 선택은 ID로
상황
훅마다 상태를 직접 고치면 누가 언제 바꿨는지 추적할 수 없었고, 선택을 객체로 들고 있으면 데이터가 갱신될 때마다 선택이 풀렸습니다.
판단
상태 변경은 노드 ID와 변경 사항을 전달하는 공통 함수 하나로 모았습니다. 선택은 ID로 관리해, 노드 객체가 새로 만들어져도 선택이 유지되게 했습니다.
바뀐 경로만 갱신한다
상황
기존 갱신 방식은 노드 하나가 바뀔 때마다 트리 전체를 순회했습니다. 노드가 1,000개 이상으로 늘어나는 경우를 고려해야 했습니다.
판단
변경 대상 노드가 포함된 경로만 갱신하고, 나머지 가지는 순회하지 않고 즉시 그대로 반환하도록 바꿔 큰 트리에서의 성능 저하 가능성을 줄였습니다.

04성과

지표 개선 전 개선 후
트리 구현 화면별로 따로 6개 화면이 공용 트리 1개 사용
트리 상태를 바꾸는 곳 훅 3곳 공통 함수 1개
데이터 갱신 후 선택 풀림 유지

설계안 제안부터 구현, 기존 화면 교체까지 맡았습니다. 이후 조회 기준이 경로에서 고유 ID로 바뀌었을 때도, 조회 책임을 화면으로 나눠 둔 덕분에 공용 트리 내부는 고치지 않고 각 화면의 조회 로직만 바꿔 대응했습니다.
