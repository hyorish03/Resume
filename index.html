직접입력 화면의 초기 로딩과 입력 지연 개선
  • 문제:화면 전용 라이브러리(Monaco·ECharts·ExcelJS)가 모든 화면에 로드됐고, 긴 SQL은 키 입력마다 0.5초 이상 지연됐습니다.
  • 판단:라이브러리 하나가 아니라 화면 전용 의존성이 공통 경로로 새는 구조를 원인으로 보고 그 경로를 끊었고, SQL 포매터는 화면에 보일 때만 실행했습니다.
  • 결과:공통 엔트리 gzip 85% 감소, FCP 7.6초 → 1.3초, 입력 지연 565ms → 24ms.
예약 폼 분기 판정 단일화로 잘못된 요청 차단
  • 문제:예약 조건 판정이 화면·검증·요청 세 곳에 따로 있어, 숨긴 값이 전송되거나 수정한 날짜가 빠졌습니다.
  • 판단:세 곳이 서로 다르게 판정하는 것을 원인으로 보고 판정을 한 함수로 모은 뒤, 검증된 값만 판별 유니온으로 좁혀 잘못된 조합을 타입에서 막았습니다.
  • 결과:잘못된 요청 차단, 27개 조건 조합 테스트로 고정.

AI Agent 기반 E2E 테스트 체계 구축체계 구축 ↗E2E 상세 ↗
  • 문제:QA 인력 없이 배포 전마다 사용자 플로우를 손으로 점검했습니다.
  • 판단:수동 검증이 이미 플로우 단위라 E2E로 그대로 옮기고, 팀원이 Playwright를 배우는 대신 AI Agent가 규칙에 따라 테스트를 작성하게 했습니다.
  • 결과:배포 전 검증 약 20분 → 약 5분, 최근 3번 배포에서 회귀 6건 사전 탐지.
트리 상태 소유권 재설계로 6개 화면의 트리 통합
  • 문제:공용 트리는 수정 영향 범위를 예측하기 어려워 화면마다 트리를 따로 만들었고, 데이터를 갱신하면 선택이 풀렸습니다.
  • 판단:세 훅이 같은 상태를 각자 수정하는 것을 원인으로 보고, 조회는 화면이, 상태는 트리가 맡게 나눈 뒤 선택은 객체 대신 ID로 관리했습니다.
  • 결과:6개 화면의 트리를 하나로 통합, 이후 조회 기준 변경에도 트리 수정 없이 대응.
위성망 고객 환경의 첫 화면 로딩 27초 → 10초
  • 문제:위성 회선을 쓰는 고객사 조건을 재현하니 채팅 첫 화면이 약 27초 걸렸습니다(사내망 1.4초).
  • 판단:첫 API를 앞당기는 방식은 이득이 0.3~0.8초뿐이라 기각하고 받는 양(약 8MB)을 원인으로 보고 nginx 압축을 적용하되, 스트리밍 응답은 압축에서 제외했습니다.
  • 결과:채팅 첫 접속 27.1초 → 약 10초, 받는 JS 5.8MB → 1.8MB (압축 전후 A/B 실측).
